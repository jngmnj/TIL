# 8강. 프롬프트와 인간–AI 협업

- 학습일: 2026-09-26
- 과목: AI 리터러시
- 주제: 프롬프트 설계, 인간–AI 협업 단계, 학습 보조와 대리 수행, 개인정보와 편향

## 핵심 요약

**프롬프트는 AI에게 질문하는 입력이면서, 해결할 문제의 목적·맥락·조건을 전달하는 수단이다.** 좋은 프롬프트는 원하는 결과에 가까운 초안을 얻는 데 도움을 주지만, 결과의 사실성이나 학습 효과를 보장하지는 않는다.

| 핵심 질문 | 확인할 내용 |
| --- | --- |
| 무엇을 해결하는가? | 목적, 범위, 대상 |
| 어떤 결과가 필요한가? | 형식, 분량, 제약, 평가 기준 |
| 어떻게 협업하는가? | 문제 설정 → 초안 생성 → 대안 탐색 → 검토 → 최종 편집 |
| 학습에 도움이 되었는가? | 자신의 이해·판단·설명 능력이 남는지 |
| 무엇을 조심하는가? | 잘못된 전제, 개인정보 입력, 편향, 검증 없는 사용 |

강의는 **AI를 얼마나 사용했는가보다 학습자가 무엇을 이해하고 판단했는가**를 중요하게 본다. 과제별 AI 사용 허용 범위는 별도로 확인해야 한다.

## 1. 프롬프트는 문제를 설계하는 입력

### 단순한 질문에서 문제 정의로

‘AI 윤리에 대해 설명해 줘’도 프롬프트다. 다만 대상·용도·범위가 없으므로 일반적인 설명이 나오거나 필요한 내용과 다른 방향으로 답할 수 있다.

문제가 구체적일수록 다음 요소를 명확하게 전달하는 것이 도움이 된다.

| 요소 | 전달할 내용 | 예시 |
| --- | --- | --- |
| 목적 | 결과를 어디에 사용할지 | 수업 발표 준비 |
| 대상 | 누가 읽거나 들을지 | 대학 1학년 비전공자 |
| 맥락 | 현재 상황과 배경 자료 | AI 윤리의 기초를 처음 배우는 상황 |
| 범위 | 다룰 주제와 제외할 내용 | 편향·개인정보·책임성 세 항목 |
| 형식 | 결과의 구성 | 항목별 설명과 일상 사례 |
| 제약 | 분량·수준·자료 사용 조건 | 쉬운 말, 항목당 사례 한 개 |
| 평가 기준 | 좋은 결과를 판단할 기준 | 정확성, 이해 가능성, 근거의 적절성 |

모든 요청에 이 항목들을 길게 나열할 필요는 없다. **과제에 필요한 정보를 명확하게 전달하는 것**이 핵심이다.

### 모호한 요청과 구체적인 요청 비교

```text
AI 윤리에 대해 설명해 줘.
```

강의에서는 위 요청을 다음과 같이 구체화한다.

```text
대학 1학년 비전공자에게 AI 윤리를 설명해 줘.
편향, 개인정보, 책임성의 세 항목으로 나누고,
각 항목에 일상 사례 한 개를 포함해 쉬운 말로 작성해 줘.
```

두 번째 요청은 대상·범위·구성을 제시하여 답변 방향을 좁힌다. 하지만 실제 결과의 품질은 모델, 제공된 자료, 작업의 난도 등에도 영향을 받으므로 프롬프트만으로 결정되지 않는다.

### 프로그래밍과의 비유

강의는 조건과 흐름을 설계한다는 점에서 프롬프트 작성을 프로그래밍에 비유한다. 다만 자연어 지시가 프로그램 명령처럼 언제나 정확히 실행된다는 뜻은 아니다.

또한 AI가 매번 가장 확률이 높은 답 하나만 출력한다고 설명하는 것은 부정확하다. 7강에서 보았듯 생성 방식에 따라 후보를 선택하는 방법이 다르며, 자연스러운 출력과 검증된 사실은 구별해야 한다.

**좋은 답은 자신의 기대에 동의하는 답과 같지 않다.** 목적에 맞으면서도 근거가 정확하고, 필요한 반론과 불확실성을 포함해야 한다.

## 2. 프롬프트를 구성하는 장치

### 역할 부여

| 역할 예시 | 요청할 수 있는 작업 |
| --- | --- |
| 설명자 | 어려운 개념을 대상의 수준에 맞춰 설명 |
| 글쓰기 코치 | 문단 구성과 표현 개선 제안 |
| 정책 분석가 | 정책의 장점·위험·적용 조건 비교 |
| 논문 심사자 | 주장과 근거의 약점, 누락된 설명 지적 |

역할은 관점과 말투를 조정하는 장치다. ‘전문가처럼 답하라’는 지시가 실제 자격이나 정확성을 부여하지는 않는다. 심사자 역할을 주었다고 비판이 모두 타당한 것도 아니므로 근거를 확인한다.

### 맥락 제공

같은 주제라도 과제·업무·발표 중 어디에 쓰는지에 따라 필요한 설명이 달라진다. 대상의 사전 지식, 이미 확인한 자료, 해결하지 못한 부분을 제공하면 불필요한 추정을 줄이는 데 도움이 된다.

다만 맥락이 많을수록 무조건 좋은 것은 아니다. 관련 없는 정보나 서로 충돌하는 조건은 답변을 흐릴 수 있다. 민감한 자료는 맥락 제공의 필요성과 별개로 입력 가능 여부를 확인한다.

### 제약 설정

| 제약 | 예시 | 검토할 점 |
| --- | --- | --- |
| 분량 | 다섯 문장 이내 | 필요한 설명이 과도하게 생략되지 않았는가? |
| 수준 | 비전공자에게 쉬운 용어 사용 | 쉽게 바꾸는 과정에서 의미가 왜곡되지 않았는가? |
| 범위 | 제공한 자료의 내용만 요약 | 자료에 없는 주장이 섞이지 않았는가? |
| 출처 | 확인 가능한 공식 자료에 근거 | 출처가 실제로 존재하고 주장을 뒷받침하는가? |
| 제외 사항 | 근거 없는 추측을 사실처럼 쓰지 않음 | 추정과 확인된 사실이 구분되었는가? |

제약은 원하는 출력의 조건을 전달할 뿐 준수를 보장하지 않는다. 특히 **‘개인정보를 출력하지 말라’는 지시는 이미 입력한 정보의 저장·이용을 통제하는 장치가 아니다.** 입력 전에 자료를 선별해야 한다.

### 평가 기준 제시

정확성, 균형성, 쉬운 설명, 사례의 다양성 등 좋은 답의 기준을 미리 제시할 수 있다. 이 기준은 AI에 대한 요청이면서 사용자가 초안을 비교하는 기준이 된다.

- 정확성: 핵심 개념과 근거가 맞는가?
- 이해 가능성: 대상이 설명을 따라갈 수 있는가?
- 사례 적합성: 사례가 개념을 실제로 보여 주는가?
- 관점의 폭: 필요한 반론이나 영향을 받는 집단을 빠뜨리지 않았는가?

평가 기준을 입력했다고 평가가 끝난 것은 아니다. AI의 자기평가 역시 검토 대상이다.

### 예시 기반 지시

원하는 입력·출력 예시를 함께 주면 길이, 어조, 항목 구성을 전달할 수 있다. 다음은 강의의 취지를 바탕으로 만든 형식 예시다.

```text
각 항목을 아래 형식으로 작성해 줘.

개념: 한 문장으로 정의
사례: 일상에서 볼 수 있는 상황
주의점: 사례에서 확인해야 할 문제

가상 사례는 가상이라고 표시하고,
실제 사건을 제시할 때는 확인 가능한 출처를 붙여 줘.
```

예시에 오류나 편향이 있으면 출력에도 영향을 줄 수 있다. 예시가 전달하려는 형식과 사실 주장을 구분하고, 서로 일관된 예시를 사용한다.

### 길이보다 명확성

긴 프롬프트라도 목적이 모호하거나 전제가 틀리면 좋은 답을 얻기 어렵다. 짧은 프롬프트도 필요한 조건을 담으면 충분할 수 있다.

## 3. 인간–AI 협업의 다섯 단계

```text
문제 설정 → 초안 생성 → 대안 탐색 → 검토 → 최종 편집
    ↑                    │        │
    └──── 필요하면 이전 단계로 돌아가 수정 ────┘
```

### 1단계: 문제 설정

사람이 해결할 목표와 범위를 정하고, AI에게 맡길 일과 직접 판단할 일을 구분한다.

| 구분 | 확인할 사항 |
| --- | --- |
| 목표 | 무엇이 해결되면 작업이 끝나는가? |
| 역할 분담 | AI의 도움을 받을 부분과 직접 수행할 부분은 무엇인가? |
| 자료 | 어떤 자료가 필요하고 입력할 수 있는가? |
| 조건 | 형식·분량·제약·평가 기준은 무엇인가? |

AI에게 문제 후보나 질문을 제안받을 수도 있다. 따라서 원문의 ‘AI는 문제를 만들 수 없다’는 표현은 능력의 절대적인 한계보다 **목표의 타당성과 채택 여부는 사람이 판단해야 한다**는 취지로 이해한다.

### 2단계: 초안 생성

AI를 활용해 목차, 문단, 아이디어 목록, 사례 후보 등을 만든다. 빠르게 여러 가능성을 살펴볼 수 있다는 장점이 있지만, 후보 생성과 실제 자료 조사·검증은 같지 않다.

생성된 통계나 사례를 확인된 조사 결과로 바로 취급하지 않는다. 사람은 목적에 맞는 후보를 비교하고 수정한다.

### 3단계: 대안 탐색

첫 초안을 바로 확정하기보다 다른 관점·구조·표현을 비교한다.

- 서로 다른 목차의 장단점은 무엇인가?
- 사례를 바꾸면 설명이 더 명확해지는가?
- 빠진 관점이나 반례가 있는가?
- 어떤 부분을 선택하거나 조합할 것인가?

대안을 많이 받는 것 자체가 목표는 아니다. 목적과 근거에 따라 후보를 좁혀야 하며, 여러 답이 서로 비슷하다고 사실성이 확인되는 것도 아니다.

### 4단계: 검토

| 관점 | 점검 내용 |
| --- | --- |
| 사실 | 개념, 수치, 날짜, 출처가 원자료와 일치하는가? |
| 논리 | 근거가 결론을 뒷받침하며 비약·모순이 없는가? |
| 가치와 영향 | 편향, 누락, 불필요한 피해 가능성이 있는가? |
| 목적 적합성 | 대상·수준·형식과 요청 조건에 맞는가? |

오류가 있으면 직접 수정하거나 추가 자료를 확인한다. 필요하면 재질문하거나 사용을 보류한다. 문제가 목표 설정에 있다면 첫 단계로 돌아간다.

AI에게 재질문하는 것은 검토를 돕는 방법이지만, 출처의 원문 확인이나 코드 실행 같은 독립적인 확인을 대신하지는 않는다.

### 5단계: 최종 편집

검토한 내용을 자신의 이해와 사용 맥락에 맞게 재구성한다. 문체·분량을 조정하고, 근거와 출처를 확인하며, 설명의 흐름을 일관되게 만든다.

단순히 단어를 바꾸는 것만으로 내용이 정확해지거나 사용이 허용되는 것은 아니다. 최종 사용자는 무엇을 채택했고 왜 채택했는지 설명할 수 있어야 한다.

강의의 ‘사람이 책임진다’는 원칙은 학습자가 검토와 제출에 책임 있게 참여해야 한다는 의미다. 모든 상황의 법적 책임이 사용자 한 사람에게만 있다는 판단으로 확대하지 않는다.

## 4. 협업 사례

### 코드 오류 설명과 수정

1. 기대한 동작, 실제 오류, 관련 코드, 실행 환경을 정리한다.
2. AI에게 오류의 의미와 가능한 원인을 설명하도록 요청한다.
3. 제안된 수정의 이유를 읽고 자신의 환경에 맞는지 판단한다.
4. 수정 후 실행·테스트하여 문제가 해결되었는지 확인한다.
5. 같은 오류를 다시 만났을 때 설명하고 대응할 수 있는지 점검한다.

AI의 코드가 항상 가장 쉬운 구현이거나 바로 실행 가능한 구현인 것은 아니다. 오류가 사라졌더라도 요구사항과 다른 동작이나 새로운 문제가 생기지 않았는지 확인한다.

### 글의 논리 점검

자신이 쓴 글은 익숙해서 빈틈을 놓치기 쉽다. AI에게 주장과 근거의 연결, 빠진 반론, 설명이 부족한 부분을 지적하도록 요청할 수 있다.

```text
아래 글의 주장과 근거를 구분해 줘.
근거가 부족한 부분과 빠진 전제가 있다면 해당 문장을 짚어 줘.
수정 제안과 그 이유를 구분하고, 원문에 없는 사실은 만들지 마.
```

제안된 비판이 실제 원문에 해당하는지 확인한 뒤 반영한다. AI의 제안을 전부 수용할 필요는 없다.

## 5. 학습 보조와 대리 수행의 경계

| 구분 | 학습 보조 | 대리 수행의 위험이 큰 사용 |
| --- | --- | --- |
| 핵심 활동 | 학습자가 읽고 이해하고 판단 | 과제가 요구하는 사고를 AI에 맡김 |
| 결과 활용 | 검토·선택·수정 과정을 거침 | 이해 없이 결과만 제출 |
| 설명 능력 | 선택한 이유와 내용을 설명 가능 | 결과는 있지만 과정 설명이 어려움 |
| 학습 점검 | 원리와 적용 능력이 늘었는지 확인 | 완성된 결과물의 존재만 확인 |

AI 사용량이나 생성된 문장의 비율만으로 경계를 확정할 수는 없다. **과제의 학습 목표, 허용 범위, 실제 수행한 사고 과정**을 함께 봐야 한다. AI가 만든 내용을 이해하더라도 해당 과제에서 금지된 사용이라면 허용되는 것은 아니다.

### 독후감 사례

- 책을 읽지 않고 독후감 전체를 생성해 제출하면 읽기·해석·근거 확인의 핵심 활동을 건너뛸 수 있다.
- 책을 읽고 자신의 해석을 작성한 뒤 반론이나 논리의 빈틈을 점검받는 것은 학습 보조로 활용할 수 있는 방식이다.
- AI가 책의 내용을 잘못 설명할 수 있으므로 실제 원문과 대조해야 한다.

### 코드 작성 사례

- 요구사항과 원리를 이해하지 않은 채 전체 코드를 받아 제출하면 설명·수정·오류 대응 능력을 기를 기회를 놓칠 수 있다.
- 오류 원인 설명, 테스트 사례 제안, 자신이 작성한 코드 검토 등에 활용할 수 있다.
- 생성된 코드의 양만으로 학습 여부를 단정하지 않고, 과제 규정과 자신의 이해·검증 과정을 확인한다.

### 학습 효과를 점검하는 질문

1. AI 사용 전보다 개념을 더 잘 설명할 수 있는가?
2. 답변의 어떤 부분을 채택하거나 제외했으며, 이유는 무엇인가?
3. 비슷한 문제를 스스로 풀거나 접근 방법을 제시할 수 있는가?
4. 오류나 반례를 발견했을 때 수정할 수 있는가?
5. 과목에서 정한 사용·표시 기준을 지켰는가?

> 보충: UNESCO의 교육·연구용 생성형 AI 지침은 인간의 주도성과 개인정보, 포용성 등을 중요하게 다룬다. 다만 이 지침만으로 개별 과제의 허용 범위를 확정할 수는 없다. [Guidance for generative AI in education and research](https://www.iicba.unesco.org/en/africa-education-knowledge-platform/guidance-generative-ai-education-and-research)

## 6. 개인정보와 편향을 고려한 프롬프트

### 입력 전에 자료 선별하기

이름·학번·연락처·건강·금융 정보나 공개되지 않은 연구·업무 자료는 그대로 입력하지 않도록 주의한다.

| 확인 단계 | 할 일 |
| --- | --- |
| 필요성 | 작업에 꼭 필요한 정보인지 판단 |
| 입력 가능 여부 | 기관 지침, 사용 권한, 서비스의 자료 처리 조건 확인 |
| 최소화 | 불필요한 식별 정보를 빼고 필요한 부분만 제공 |
| 대체 | 판단이 어려우면 가상의 사례로 바꾸거나 입력 보류 |

이름을 지우거나 가명으로 바꾸었다고 항상 개인을 식별할 수 없게 되는 것은 아니다. 다른 정보의 조합으로 식별될 가능성도 고려한다. 실제 자료를 넣은 뒤 ‘비밀로 해 달라’고 요청하는 것으로 보호가 보장되지는 않는다.

### 질문에 숨어 있는 전제 점검하기

| 질문 | 문제 또는 개선 방향 |
| --- | --- |
| AI는 왜 항상 위험한가? | ‘항상 위험하다’는 결론을 전제 |
| AI 활용의 장점과 위험은 무엇인가? | 비교할 관점을 열어 둠 |
| 어떤 조건에서 이점이나 위험이 커지며 근거와 반례는 무엇인가? | 적용 조건과 근거까지 검토 |

다양한 관점을 요청하되, 근거가 약한 주장과 충분히 뒷받침된 주장을 기계적으로 같은 비중으로 다룰 필요는 없다. 균형은 단순히 찬반의 개수를 맞추는 일이 아니다.

누구의 관점이 빠졌는지, 특정 집단에 대한 고정관념이 질문에 들어 있지 않은지 살핀다. 질문을 개선해도 모델이나 자료의 편향이 모두 없어지는 것은 아니므로 출력도 검토한다.

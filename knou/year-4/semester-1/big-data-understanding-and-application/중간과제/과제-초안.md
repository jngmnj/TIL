# 빅데이터의 이해와 활용 중간과제

> 작성일: 2026-10-28. **1번 오류 교정 답안은 작성했고, 2번은 실제 시각화 결과 확보 전이다.** 사용자가 확정한 학과·주제는 **컴퓨터과학과 + 인공지능**이다. 현재 문서는 완성된 제출본이 아니다.

## 1. 웹 스크래핑과 오픈 API에 관한 오류 교정

### 1.1. 잘못된 부분과 이유

**첫째, 웹 스크래핑을 매우 안정적이고 반영구적인 방식이라고 단정한 것은 잘못이다.** 웹 스크래핑은 웹페이지에서 필요한 데이터를 프로그램으로 추출하는 방식이다. 예를 들어 HTML의 특정 요소를 CSS 선택자나 XPath로 찾을 수 있다. 이러한 추출 규칙이 페이지 구조에 의존하므로, 구조나 요소 이름이 바뀌면 규칙을 수정해야 한다는 결론을 도출할 수 있다. 접근 차단도 가능하다. 서울버스 개발자 역시 지역별 버스정보 사이트를 앱에 연결했다가 한 지역에서 사용이 차단된 경험을 기록했다. 따라서 자동화가 가능하다는 사실을 지속적인 안정성이 보장된다는 의미로 해석해서는 안 된다. [Scrapy 공식 문서][S1], [서울버스 개발자 기고][S2]

**둘째, 법적·윤리적 문제가 전혀 없다는 설명도 잘못이다.** 인터넷에서 볼 수 있다는 사실과 제한 없이 수집·재이용할 수 있다는 사실은 다르다. 개인정보보호위원회는 공개된 데이터에도 개인정보가 포함될 수 있음을 전제로 처리 기준을 제시했다. 수집·이용 근거와 권리 침해 가능성 등을 검토해야 하므로 스크래핑을 일률적으로 적법하거나 위법하다고 단정할 수 없다. 또한 robots.txt는 크롤러의 접근 규칙을 전달하는 장치이며, 그 규칙 자체가 접근 권한을 부여하는 것은 아니다. 따라서 수집 정책을 지키는 것과 모든 법적 문제가 해결되는 것을 구분해야 한다. [개인정보보호위원회][S3], [RFC 9309][S4]

**셋째, 오픈 API가 실시간 데이터를 제공할 수 없다는 주장은 틀리다.** API는 제공자가 정한 요청과 응답 방식으로 프로그램 간 데이터를 전달하는 인터페이스다. 실시간성은 API라는 형식 자체가 아니라 원천 데이터의 생성·갱신 주기와 전달 지연에 달려 있다. 서울시 버스위치정보조회 서비스는 제공유형을 OPEN API로, 업데이트 주기를 실시간으로 명시하고 있다. 이는 지문의 주장에 대한 직접적인 반례다. 다만 모든 API가 지연 없이 실시간 정보를 보장한다는 뜻도 아니다. [서울교통빅데이터플랫폼][S5]

**넷째, 공공기관에서 오픈 API 활용 사례를 찾기 어렵다는 설명은 실제 사례와 맞지 않는다.** 서울시 버스위치정보 API처럼 공공기관이 정보를 개방하고 민간이 서비스에 활용할 수 있는 사례가 존재한다. API에는 신청이나 인증, 이용조건이 있을 수 있지만, 절차가 있다는 이유로 공공 활용이 어렵거나 존재하지 않는다고 일반화할 수 없다. 해당 서비스 역시 공공데이터포털의 활용신청 경로를 안내한다. [서울교통빅데이터플랫폼][S5]

**다섯째, 2009년 서울버스와 2020년 공공마스크 앱을 동일한 스크래핑 사례로 묶은 것은 오류다.** 서울버스 개발자 유주완은 2009년 지역별 버스정보 웹사이트와 앱을 연결했다고 직접 설명한다. 따라서 초기 웹사이트 기반 정보 활용은 인정해야 하며, 이를 처음부터 정식 오픈 API만 사용한 사례로 바꾸어 쓰는 것도 부정확하다. 다만 이 기록만으로 모든 지역에서 같은 HTML 파서를 사용했다거나 수작업으로 정보를 복사했다는 세부 구현까지 확정할 수는 없다.[S2] 반면 2020년 공적 마스크 정보는 건강보험심사평가원의 데이터를 한국정보화진흥원이 재가공하고, 네이버 클라우드가 오픈 API로 제공하여 민간 개발자가 웹·앱을 만드는 구조였다. 이를 서울시 버스정보 사이트의 스크래핑으로 설명하면 정보의 대상과 제공기관, 전달방식을 모두 혼동하게 된다.[S6]

**여섯째, 두 사례를 모두 공공데이터 관련 법률이 없던 시기의 사례로 설명한 것은 연도상 잘못이다.** 「공공데이터의 제공 및 이용 활성화에 관한 법률」은 2013년 7월 30일 제정·공포되어 같은 해 10월 31일부터 시행되었다. 2009년은 해당 법 시행 전이지만 2020년은 시행 후다. 또한 법 시행 여부만으로 특정 앱이 스크래핑을 썼는지 API를 썼는지를 판단할 수 없다. 법의 제정 시점과 개별 서비스의 기술 구현은 별도로 확인해야 한다. [국가법령정보센터][S7], [한국법제연구원 법령 연혁][S8]

### 1.2. 교정하여 다시 쓴 설명

웹 스크래핑과 오픈 API는 모두 인터넷 데이터를 수집하는 데 활용되지만, 데이터에 접근하는 방식과 유지관리 조건이 다르다. 웹 스크래핑은 웹페이지 등에서 필요한 내용을 프로그램으로 추출한다. HTML 요소를 선택해 내용을 읽는 방식에서는 페이지 구조가 바뀌면 추출 규칙도 수정해야 하므로 반영구적인 안정성을 보장할 수 없다. 접근 제한과 개인정보 등 관련 권리도 검토해야 한다.[S1][S3]

오픈 API는 제공자가 공개한 인터페이스를 통해 필요한 데이터를 요청하고 응답받는 방식이다. 서울시 버스위치정보처럼 실시간 정보를 제공하는 공공 API도 있다. 다만 갱신 주기와 이용조건을 확인해야 하며, API가 존재한다고 모든 데이터가 무제한·무지연으로 제공되는 것은 아니다.[S5]

2009년 서울버스는 지역별 버스정보 웹사이트의 정보를 앱에 연결한 초기 공공정보 활용 사례이며, 접근 차단 경험은 안정적인 정보 개방의 필요성을 보여준다.[S2] 2020년 공공마스크 앱은 공공기관의 판매정보를 재가공하고 오픈 API로 제공한 민관협력 사례다.[S6] 두 사례는 수집·제공 방식과 시점이 다르다. 2013년 시행된 공공데이터법을 고려하면 두 사례 모두 법 시행 이전이었다고 설명할 수도 없다.[S7][S8] 결국 적절한 수집 방법은 데이터의 제공 방식, 갱신 주기, 이용조건과 서비스 목적을 함께 고려해 선택해야 한다.

### 2.2. 뉴스량 변화와 실제 사건 분석

**실제 시계열 확보 후 작성해야 하는 답안이다.** 현재 급증·급감 날짜와 기사 수를 확인하지 못했으므로 특정 AI 사건을 원인으로 단정하지 않는다.

| 필요한 증거 | 현재 상태 |
| --- | --- |
| 급증·급감 구간과 전후 기사 수 | 미확보 |
| 해당 구간의 실제 기사 제목·언론사·게시일 | 미확보 |
| 사건 발생일과 확인 가능한 발표·기사 | 미확보 |
| 컴퓨터과학과 또는 관련 산업과의 연결 | 사건 확인 후 분석 |

결과를 확보하면 ‘변화 구간과 수치 → 기사에 나타난 사건 → 학과·산업과의 관련성 → 다른 설명과 한계’ 순서로 답안을 완성한다. AI 관련 유명 사건을 먼저 골라 그래프에 나타난 것처럼 기술하지 않는다.

### 2.3. 관계도와 비즈니스 의사결정 의견

**실제 관계도 확보 후 작성해야 하는 답안이다.** 핵심 개체명, 연결된 개체, 연결선 두께와 플랫폼의 설명을 확인한 후 해석한다.

현재 설정할 수 있는 분석 질문은 ‘컴퓨터과학 분야의 인공지능 보도에서 연구·교육·기업 중 어떤 주체와 쟁점이 연결되는가?’이다. 이는 분석 질문이며 실제 관찰 결과가 아니다. 관계도와 관련 기사를 확보한 뒤 교육과정, 기업 협력, 서비스 도입 등에서 어떤 선택이 타당한지 의견을 제시하고 본인의 판단을 반영한다.
